# 自动排班搜索与验证

本工作分支的自动排班优化固定布局下的人员和主替安排，以完整仿真采样窗口内的日均加权产出为最终比较标准。合法占位、已有人员锁定、组合完整、实际技能阶段和恢复容量是约束，不参与收益取舍。现有排班的独立收益计算与本入口分别运行。本轮交付限于新分支本地提交，不更新 `main` 或 `D:\Tools\R.I.I.C-Calculator`。

## 默认搜索

1. **构造一份合法初始表。** 按实际干员库完成组合、主替、宿舍、辅助工位和跑单候补配置，并在计算前写入有效的暖机与恢复策略。内部构造仍可比较组合骨架，但只交出一份初始排班，不再准备固定 6+2 套完整排班。
2. **建立完整队伍域。** 从初始表提取受支持的制造组，枚举完整队伍及合法的组、房间、主替落点。人员资源集合与实际工位顺序分别保存，固定复杂块不参与重分配。估值前用纯结构动态规划检查组、房间与核心覆盖；只有完整证明某类队伍不可能组成合法完整分配时才排除，未完成的筛选不删除任何队伍。
3. **计算有限周期系数。** 在与最终比较一致的预热、采样窗口内，按实际技能、心情上下限、暖机和恢复策略计算主队工休轨迹，以及替队在兼容周期内的产出。该条件模型使用固定外部环境和参考床位/恢复条件，不包含完整调度中的所有等待、竞争或全局联动变化。
4. **联合指派与解码。** 动态规划处理组、房间、主替和必留核心覆盖，再对重复使用同一干员的冲突进行分支。只把选中的已量化列交给事务解码，再核对原用户约束、库存、完整组合、暖机、物理占位、床位容量和编译诊断。求解内部仍会搜索分支，不是一个闭式公式。
5. **最多两份完整仿真确认。** 对初始表与至多一份不同的计算结果使用相同预热、采样、种子、无人机目标和权重，默认 24h 预热加 72h 采样。只有成功完成且评分有限的结果参与比较，保留日均加权产出较高者；组合偏好和单站效率仅作同分排序。没有可接受的计算结果时，仍可验证初始表。

直接返回胜出排班及其同次仿真报告。默认不追加主替改写、散件置换或邻域搜索；显式开启的第三阶段会增加比较和完整仿真，不属于上述默认两份范围。旧设置中显式开启的选择保留；`trials`、`simulationTopK` 等旧字段仅兼容保存，不再控制默认完整排班数量。

## 支持范围与预算

当前联合重分配仅支持已建、生产赤金或作战记录、1–3 工位且每房一个完整换班组的制造站，每个槽位有一个普通物理替班。房号、容量、实际人员和技能阶段都从输入推导，不固定为 243 布局，也不把缺失库存记录补成满练。多绑定、同房拆组、跨多个制造房的复杂核心、永久制造主班、锁定块及固定菲亚梅塔/外部候补引用涉及的块保留原样；固定跨站支持仍保留原房、原位和绑定。

用户原始排班已有完整核心的产品、成员以及锁定人员和位置是强约束。内部构造的其他核心可以整组弃选；同一组合的实际合法产品变体具有相同固定外部核心、同支持组且有共同本地核心时，也允许整体换用变体。共同核心必须完整保留，旧变体独占而新变体不需要的成员可以释放到其他合法队伍。例如内部自动化赤金组可保留固定承曦格雷伊支持、整体转换为合法经验组并释放清流；用户原有赤金组合不会因此被改写。两个完整核心也可以在合法的同一队伍中共存。

队伍枚举、周期估值和指派搜索各有数量、工作量或时间预算。达到预算时明确记录中止原因，只使用已经完整量化的队伍和周期兼容关系；初始可行表继续保留。未完成的枚举不能称完整库，未量化列不能按零收益混入，当前量化子域的最优也不能称原始完整域最优。没有支持域、没有可行指派或解码失败时保留初始排班及诊断。

并行仿真先派发主替初始正耗速较高的任务，以减少长任务留在队尾的等待。该特征仅估计事件密集程度，不参与收益筛选，也不代表运行时间上界。每项作业使用自己的库存与技能阶段；不能评估时保持普通优先级。全部输入、种子及采样窗口不变，完成结果和进度映射回原候选索引，同步入口保持原顺序。

完整候选去重包含设施、分组、恢复策略、候补和顺序。单次任务只缓存完整、有限评分的模拟结果，缓存键包含完整输入及仿真设置，不将旧方案的报告附到修改后的方案。

## 暖机与休息

自动生成按实际持有练度和工作设施识别有明确数值暖机机制的技能，为暖机主班追加 `exhaust_require`。制造、发电和伊内丝等明示的线索效率暖机仍正常计算。裁缝、线索倾向等没有明示暖机曲线的机制按最高档处理，沿用既有固定概率/计数模型，不新增暖机损失或自动耗尽要求；用户已有的耗尽配置保留。训练室目前只模拟闲置进驻，不执行训练任务，因此不按训练任务的累计时长技能配置耗尽。

原有人员锁定、整组关系和其他配置保留；显式永久工作人员继续使用其既有策略。组内一个主班采用耗尽策略即可让整组跳过普通心情阈值。多个成员采用耗尽时，由最早需要休息的成员触发整组，因此不保证每个人都恰好耗至零或都达到自己的暖机上限。

普通替班会在原主班回岗时被替换，仅追加耗尽标记不能改变该行为。自动构造和主替调序会避免把暖机干员分配成这类短时替班；已有锁定暖机替班、策略未覆盖的跨设施/跨组主位替换引用或暂不支持的多绑组会报告原因，保留原配置。策略必须在仿真前写入工作区，最终返回同一输入的报告。

## 最优性的范围

默认流程返回**初始表与计算结果中已完成完整仿真验证的较优方案**。周期模型的目标用于计算一个分配决定，完整仿真（F）的日均加权产出才决定采用哪份表；二者不能互换。

动态规划和冲突分支给出的上界、差距与 `optimalityProven` 仅适用于传入的有限量化系数模型。即使求解完成，也仍受队伍域、固定背景、参考恢复条件和数值积分假设限制；这些上界不是完整 F 的收益上界。要证明完整 F 最优，还需要覆盖全部合法配置并证明模型与完整调度等价，当前实现没有这项证明。

求解代码为本地 TypeScript 模块，不依赖服务端、外部 LP/MIP 求解器或网络加载。同步公开入口仍是同步计算，浏览器界面通过 Worker 执行；预算检查不构成每个宿主环境的实时耗时保证。固定种子控制仿真随机过程，但时间预算下实际完成的计算范围仍可能随宿主负载变化，重现结果须同时保留选中排班、请求和预算状态。

## 比较方法

新旧版本必须固定布局、实际练度、权重、无人机设置、种子以及完整预热和采样窗口。候选预算与是否开启第三阶段属于算法差异，应单独列明，不能用缩短采样或改收益权重制造提升。

记录完整评分、有效与失败候选数、正式模拟调用次数、墙钟耗时、进程 CPU 时间和输入/源码哈希。并行运行其他任务会影响墙钟耗时；模拟次数是独立的工作量指标。中止运行保留部分记录，不作为完整算法结果。单元测试、Node 正式模拟、浏览器 Worker 和真实游戏的证据范围分别说明。

使用 `scripts/benchmark-auto-roster.mjs` 对保存的输入运行正式优化器，输出目录必须尚不存在：

```powershell
node scripts/benchmark-auto-roster.mjs --request artifacts/request.json --out artifacts/roster-comparison/new --concurrency 4
node scripts/benchmark-auto-roster.mjs --request artifacts/baseline-request.json --source-root artifacts/baseline-source --out artifacts/roster-comparison/old --concurrency 4
```

输入包含 `workspace`（或 `base`）、`entries`、`options`，并显式指定 `simulationWarmupHours` 与 `simulationSampleHours`。脚本原样传递选项，只对独立打包源码增加观测，不改源码树、输入或旧结果。`source-manifest.json` 固定实际读入文件和 bundle 的哈希；`events.jsonl`、`result.json`、`summary.json` 保留实际进展、完整结果和统计。仿真引擎调用与候选入口调用分别计数，不相加；直接桥接回退仍计入引擎调用。并发数相同仍不足以消除宿主机其他负载，稳定耗时比较应单独顺序运行。
